# 2 The Rough Basic Idea of the Application

The application implemented for this assignment lets the user activate and deactivate *tasks* through *task elements* presented in the user interface (UI). Based on the start and end times of the *activity intervals* recorded through these activations and deactivations, various time usage information related to *tasks* (and associated *tags*) is presented to the user. The application allows the addition, deletion, and modification of *task elements* and *tags* through its UI.

Figure 1 illustrates the basic idea and structure of the application along with some key concepts. Note that the backend server (with the database functionality) depicted in the figure is provided for you. (Do not modify it!) You are to implement the frontend part only, which is to communicate with the server using the provided REST API.

> **[Figure 1: The basic idea. Note that the UI part should also contain, e.g., navigational elements and be able to show different views as instructed, although the figure, for simplicity, only illustrates a view showing some *task elements*.]**

The UI is able to visually present *task elements* (corresponding to the *tasks* known by the system), which the user can activate and deactivate. (“Start” and “Stop” buttons in Figure 1 are meant for this, but you are free to use some other sensible way, too, if you wish.) The application reads its initial state through a REST API exposed by a server application provided by the course staff. The server is also used to save the changes made by the user.

### 4.2.2 Miscellaneous Clarifications, Highlights, and Grounds for XP Penalties

Fulfilling some module requirements only partially does not generally yield any XPs for that module. Erroneous behavior clearly related to a particular requirement may prevent getting the corresponding module XP. Therefore, pay attention to every single requirement and implementing them without (major) bugs!

The overall XP score for the assignment is determined by the sum of the gathered module XPs possibly modified by XP reductions that may be applied based on, e.g., minor bugs or bugs not directly related to the requirements, grave UX problems, (unnecessary) browser warning and errors, misleading marks in the *`implemented.md`* file for unimplemented modules, or deviations from following the instructions (concerning, e.g., the code quality or something else).

In this assignment, all the points in time presented in the application UI are to be understood as being expressed in the computer’s local time. Likewise, timestamps handled by the API and stored in the database by the server should be interpreted as local times in the same time zone. So, although UTC time is often used to store timestamps in real-world scenarios, the application to be created in this assignment should not convert times to a different time zone at any point. (The server does not make conversions, and the frontend application should not either.) Pay attention to testing that the application behaves correctly (at least when running in a computer set to the Finnish time). (If not, some XP penalties may be applied.)

The API must be used “correctly” (i.e., as in the documentation/examples). Deviations from the expected usage may lead to unexpected/erroneous behavior. (Do not, e.g., store *tag texts* directly in *tasks* – the API is designed to handle *tags* separately, and the application should use it accordingly.) If the application does not interpret the data obtained from the API correctly, it may lead to erroneous behavior during the tests and thus to XP penalties.

Modules K, L, and M do not yield any XPs, if the related time information is not correctly read from the API. (In such a case, these functionalities cannot be easily tested.)
